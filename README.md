# Информационная система управления закупками и учёта поставщиков

Десктопное приложение отдела закупок ЗАО «Карачаевский пивзавод» (дипломная работа).
Автоматизирует закупки сырья и материалов: справочник поставщиков, заявки и заказы, контроль сроков, приёмка поставок, склад, рейтинг поставщиков, отчёты.

> Принцип: человек принимает решения (выбор поставщика, отправка заказа, приёмка), всё остальное система делает сама — заявки по остаткам, подстановка цен и дат, контроль просрочек, обновление склада, пересчёт рейтинга, отчёты.

## Вход в систему

| Логин | Пароль |
|---|---|
| `admin` | `admin` |

Учётная запись создаётся при первом запуске. Пароль меняется в разделе **Настройки**. Пароли хранятся только в виде хеша (bcrypt).

При первом запуске программа загружает **демонстрационные данные** (6 поставщиков, 13 материалов, ~60 заказов за 11 месяцев с приёмками, оценками качества, просрочками и списаниями). Заменить данные демонстрационными позже можно в *Настройки → Демонстрационные данные*.

## Технологии

Electron (electron-vite) · React + TypeScript + Vite · Tailwind CSS · TanStack Table · Recharts · lucide-react · SQLite (better-sqlite3) · Drizzle ORM + drizzle-kit · Zod · bcryptjs · exceljs · electron-builder.

### Архитектура

```
src/main        процесс Electron: БД, бизнес-логика (сервисы по модулям), IPC, PDF, резервные копии
  db/           схема Drizzle, подключение + автоматические миграции, демо-данные (seed)
  services/     auth, materials, suppliers, requests, orders (+приёмка), rating, reports, excel, dashboard, backup, audit, settings
src/preload     contextBridge: типизированный window.api.<модуль>.<метод>()
src/renderer    React-интерфейс (к базе напрямую не обращается)
src/shared      типы, подписи и Zod-схемы — общие для интерфейса и main (валидация и там, и там)
drizzle/        SQL-миграции (генерируются drizzle-kit)
scripts/        selftest.ts — проверка бизнес-логики
```

`contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. Файл базы — `zakupki.sqlite` в `app.getPath('userData')`. Миграции применяются при каждом запуске. Работа идёт через ORM, поэтому переход на PostgreSQL — смена драйвера.

## Запуск и сборка

Требуется Node.js 22+.

```bash
npm install
npm run dev          # запуск в режиме разработки
npm run typecheck    # проверка типов
npm test             # самопроверка бизнес-логики (23 проверки)
npm run db:generate  # создать миграцию после изменения src/main/db/schema.ts
npm run dist         # установщик Windows (NSIS) → папка release/
```

Установщик собирается на Windows (`npm run dist`) либо в GitHub Actions: workflow **«Сборка установщика Windows»** (запуск вручную, результат — артефакт `installer`). better-sqlite3 использует готовые N-API-бинарники, компилятор C++ не нужен.

## Модули

- **Дашборд** — расходы за месяц, активные/просроченные заказы, материалы ниже минимума, график расходов за 12 месяцев, топ-5 поставщиков, блок «Требует внимания» (клик ведёт к записи).
- **Материалы** — номенклатура и склад. Остаток меняется только движениями: приход при приёмке, расход при списании. Материалы ниже минимума подсвечиваются; для них автоматически создаётся заявка (если нет открытой заявки или активного заказа). История движений.
- **Поставщики** — справочник, прайс (цена и срок доставки), карточка с рейтингом по критериям, процентом поставок вовремя и средней оценкой качества. Удаление поставщика с заказами запрещено — только деактивация.
- **Заявки** — ручные и автоматические (с пометкой «Автоматически»), кнопка «Создать заказ».
- **Заказы** — номер `З-ГГГГ-NNNN`, статусы `Черновик → Отправлен → Частично получен → Получен` и `Отменён`. При создании из заявки показывается список поставщиков материала по убыванию рейтинга с ценой и сроком; цена, ожидаемая дата (сегодня + срок поставщика) и количество подставляются автоматически. Просрочка вычисляется (ожидаемая дата прошла, заказ не получен) и подсвечивается красным. Таблица с фильтрами и канбан-доска. Печать и сохранение в PDF.
- **Приёмка** — фактическое количество по позициям, оценка качества 1–5, комментарий. После приёмки: остатки растут, статус заказа обновляется, связанная заявка закрывается, рейтинг пересчитывается.
- **Отчёты** — расходы (по поставщикам, категориям, месяцам; таблица и график), рейтинг, просроченные поставки, движение материалов; экспорт любого отчёта в Excel.
- **Настройки** — смена пароля, веса рейтинга, резервная копия и восстановление.
- **Журнал** — создание и изменение заказов, смена статусов, приёмка, списание, изменение настроек.

## Рейтинг поставщиков

**Рейтинг = (w₁·Ц + w₂·С + w₃·К) × 10**, веса по умолчанию 0,4 / 0,3 / 0,3 (сумма должна быть равна 1, меняются в настройках).

- **Ц (цена)** — по каждому материалу, который поставлял поставщик, отношение минимальной цены среди всех поставщиков этого материала к цене данного; результат усредняется (0–1).
- **С (сроки)** — доля поставок (приёмок), принятых не позже ожидаемой даты заказа (0–1).
- **К (качество)** — средняя оценка качества при приёмке / 5 (0–1).

Пока поставок не было, показывается «Нет данных». Рейтинг кэшируется в таблице `suppliers` и пересчитывается после каждой приёмки, при изменении весов и при изменении прайсов.

## Принятые решения

- «Расходы на закупки» считаются по заказам в статусах «Отправлен», «Частично получен», «Получен» — по дате отправки.
- Автозаявка создаёт заявку «Новая» с пометкой «Автоматически» на количество, возвращающее остаток к двум минимумам.
- Отмена заказа возвращает связанную заявку в «Новая», если активных заказов по ней не осталось.
- Приёмка может быть частичной: недопоставку можно принять следующей приёмкой; каждая приёмка учитывается как отдельная поставка в критерии «Сроки».
- Резервная копия — полноценный файл SQLite (`.sqlite`), создаётся средствами самой СУБД (согласованная копия при работающем приложении). Перед восстановлением рядом сохраняется `zakupki.sqlite.before-restore`.
